# ECController v1.0.3

发布日期：2026-09-23

本版合并了 **1.0.2 的界面性能优化**（该版本未公开发布）与 **本次的启动崩溃修复**。

> **如果你正在用 v1.0.1，建议升级。**
> v1.0.1 存在一个启动崩溃缺陷：只要 WinRing0 驱动当前没被加载（例如刚重启过机器），
> 双击程序就会**无提示地直接退出**，看起来像「程序打不开」。详见下节。

## 一、修复：首次启动无提示崩溃（严重）

### 症状

双击 `ECController.exe`：
- 没有窗口，没有错误弹窗，没有任何提示；
- 进程一秒钟内自己消失；
- `Logs\` 里的日志停在「驱动服务已存在，改为直接打开。」这一行，后面一个字都没有。

### 根因

`DriverLoader.TryQueryServiceImagePath()` 用 `QueryServiceConfig` 读已注册服务的驱动路径时，
把缓冲区**第一个字段**当成了 `lpBinaryPathName` 指针：

```csharp
// 错误写法
IntPtr pathPtr = Marshal.ReadIntPtr(buffer, 0);
```

但 `QUERY_SERVICE_CONFIGW` 的字段顺序是：

```c
typedef struct _QUERY_SERVICE_CONFIGW {
  DWORD  dwServiceType;       // ← 偏移 0
  DWORD  dwStartType;         // ← 偏移 4
  DWORD  dwErrorControl;      // ← 偏移 8
  LPWSTR lpBinaryPathName;    // ← 偏移 16（x64），这才是路径
  ...
```

于是偏移 0 读到的实际是 `dwServiceType | (dwStartType << 32)` = `0x0000000300000001`，
一个纯粹的垃圾值。把它交给 `Marshal.PtrToStringUni` 解引用 → `AccessViolationException`。

**致命之处在于它拦不住。** 在 .NET Framework 4 里这类异常属于「损坏状态异常」，
`catch (Exception)` 捕获不到，进程当场被终止 —— 所以既没有日志也没有弹窗。
只有 Windows 事件日志里留了一条 `.NET Runtime` 1026：

```
应用程序: ECController.exe
Framework 版本: v4.0.30319
说明: 由于未经处理的异常，进程终止。
异常信息: System.AccessViolationException
   在 System.String.wcslen(Char*)
   在 System.Runtime.InteropServices.Marshal.PtrToStringUni(IntPtr)
   在 ECController.Driver.DriverLoader.TryQueryServiceImagePath(IntPtr, System.String ByRef)
   在 ECController.Driver.DriverLoader.EnsureServicePointsAtCurrentDriver(IntPtr, System.String)
   在 ECController.Driver.DriverLoader.InstallAndStartDriver(System.String)
   在 ECController.Driver.DriverLoader.InitializeDriver()
   在 ECController.Services.EcService.Initialize()
   在 ECController.MainForm.InitializeEc()
   在 ECController.MainForm.MainForm_Load(...)
```

### 为什么时好时坏

这条代码只在「设备打不开 → 走安装/修复流程」时才被执行：

| 情形 | 行为 |
|---|---|
| WinRing0 驱动**已经加载**（例如刚用过、没重启） | 第 1 步 `TryOpenDriver` 就成功，直接返回，**碰不到这段代码** → 一切正常 |
| 驱动**没加载**（重启后第一次运行） | 进入安装流程 → 命中该分支 → **静默崩溃** |

所以这个缺陷被「机器一直没重启」掩盖了很久。**装好程序后第一次重启，必然踩到。**

### 修复

- 按真实字段布局取指针（偏移由编译器算出，不写死数字）；
- 解引用**之前**校验指针落在缓冲区内，越界一律返回 `null` 而不是去读野指针；
- 查询失败/读不到路径时写 `WARN` 日志，不再静默返回；
- 新增兜底异常记录（`AppDomain.UnhandledException` / `Application.ThreadException`），
  普通未处理异常至少能留下日志。
  *注意：损坏状态异常（含本次这类）依旧无法被托管代码捕获，真正的防线是上面那两条。*

### 回归测试

`ECControllerTests` 新增 14 项，其中 8 项直接钉住这个 bug：

- `lpBinaryPathName` 偏移必须是 16（x64）/ 12（x86）；
- 偏移 0 读到的必须是 `0x0000000300000001` 这类垃圾值，**且不等于**正确偏移处的指针；
- 越界指针 / 空指针 / 缓冲区过小 / 空缓冲区 → 一律返回 `null`，不得解引用；
- 另外 6 项拿**真实的** `WinRing0_1_2_0` 服务做只读查询（普通权限即可，不启动服务），
  验证生产代码能从真实 `advapi32` 返回的缓冲区里读出正确路径。

## 二、界面性能优化（1.0.2 的内容）

**优化前（1.0.1）**：拖动窗口约 87 ms/帧（≈7 FPS），明显发涩。

两个真元凶：

| 元凶 | 代价 | 处置 |
|---|---|---|
| 客户区「壁纸模糊」底纹，`OnMove` 每移动 8px 整块重算 | 单次 49.5 ms | 整条移除，改为一次线性渐变填充（0.65 ms） |
| `pnlBootGroups` 使用了 `Transparent` 背景 | 单独占整窗重绘 13.5 ms | 改为卡片白（8.8 ms） |

**优化后（1.0.3）**：

| 指标 | 1.0.1 | 1.0.3 |
|---|---|---|
| 拖动每次位移 | 87 ms | **0.72 ms** |
| 客户区背景绘制 | 49.5 ms | **0.65 ms** |
| 整窗重绘 | 35 ms | **~30 ms** |
| GDI 句柄增量 | — | **0** |

整窗重绘剩下的 ~30 ms 是原生控件的固有成本（4 个 `ComboBox` 纯原生绘制就占 8.9 ms），
不是自绘代码的问题。`tests\PerfProbe.cs` 已把上述指标固化成断言。

### Mica 效果的处置

不是全删，是拆开：

- **标题栏的真 Mica 保留**（由 DWM 合成器绘制，不占本程序 CPU）——这是免费的美观；
- **客户区的「模拟 Mica」删除**——那是在自己进程里贴位图做模糊，唯一的重开销来源。

新增 `config.json` 配置项：

```json
"MicaTitleBar": true
```

默认开启。设为 `false` 可关闭标题栏材质（老配置里没有这个键时按开启处理）。

客户区改为纯色垂直渐变（`#FAFBFD` → `#E9EEF4`），观感与旧版接近但成本可忽略。
`tests\UiDiag.cs` 新增像素级断言：渐变两端取色零误差、卡片圆角外侧与窗体底色一致。
